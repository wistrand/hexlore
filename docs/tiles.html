Elements tiles: layout, protocol and touch mapping

What the server in src/server.mjs knows about the Nanoleaf Elements hexagons, and how it turns touches on the panel into input. Findings are from one NL52 controller on firmware 12.4.1; items marked inferred have not been confirmed by Nanoleaf.

The tile

Each hexagon has six LEDs, one in each corner, and one capacitive touch sensor. The LAN API knows the LEDs as six separate zones with their own ids; the touch sensor reports under a seventh id that appears nowhere in the layout.

Layout

GET /api/v1/<token>/panelLayout/layout returns sideLength (67) and positionData, one entry per zone:

{"panelId": 20201, "x": 201, "y": 158, "o": 360, "shapeType": 15}

Zones are grouped into tiles by geometry, not by list order: the tile center is (x, y) minus 50 units in direction o, and zones whose centers agree belong together. o is not reduced modulo 360 (values from 60 to 660 occur); it is o mod 360 that gives the direction, while the raw value orders the corners (see Ids). y points up. When tiles are added or rotated the controller recomputes the whole layout and may shift every coordinate; ids stay with the hardware.

Streaming (extControl v2)

The server switches the device to extControl with PUT /effects and then sends UDP frames to port 60222, on every change and once a second as a keepalive:

FieldSizeMeaning
countu16number of zone records
panelIdu16zone id from the layout
r g b w4 x u8color; w unused
transitionu16fade time in 100 ms units; 0 is a hard cut

All values big-endian. One record per zone, 8 bytes each; the whole layout fits in one packet.

Touch protocol

Touch comes in two forms. The server opens the gesture stream with a header, and the device then streams raw touch data over UDP for as long as that connection stays open.

GET /api/v1/<token>/events?id=4
TouchEventsPort: 40555

Gestures (SSE on the same connection)

id: 4
data: {"events":[{"panelId":-1,"gesture":5}]}

panelId is always -1 on Elements, so gestures carry no tile. Seen: 2 (swipe up) and 5 (swipe right), numbered as in Nanoleaf's documentation. The server ignores these.

Raw touch (UDP to the port named in the header)

Packets arrive about 7 times a second while anything is touched or near a tile, several records per packet when several tiles are involved. Resolution is one reading per tile, not per corner.

Corner ids and touch ids

The touch id is not in the REST layout, but it can be computed from the tile's corner ids. Model fitted to 20 tiles mapped by hand; it predicted the ids of tiles added later, and it matches all 29 tiles in three sample layouts from other installations found in the Nanoleaf Android app. The app was decompiled and analyzed with cupella, which is also how the hexagon-level id described below was found.

The touch id is the hexagon's own panel id. The app's internal layout lists each tile as an APEX_HEX entry (shape type 14) next to its six APEX_KITE corner zones (type 15); the REST API leaves the type 14 entries out. In that layout the hexagon's o is the first kite's o minus 60.

  1. Sort a tile's six corners by raw o, rising. Call the first corner's hidden counter value j.
  2. Corner i has id K ^ L(j + i) for i = 0 to 5, and the touch id is K ^ L(j + 6). K is a per-tile constant, L is the same for every tile.
  3. L is the linear part of a reflected CRC-16 with polynomial 0x8005 (the CRC-16/ARC, MODBUS, USB and MAXIM family) over a little-endian counter. It is linear over XOR, so L(a ^ b) = L(a) ^ L(b), and it is fixed by its values on powers of two:
k0123456789101112131415
L(2^k)90c16181c302c607cc0dd819f031a06100c10182030406080c10182030406080

Because K cancels, the XOR of two neighboring ids is L((j+i) ^ (j+i+1)), and n ^ (n+1) is always of the form 2^m - 1: 1 when n is even, 3 when n ends in 01, 7 for 011, 15 or more when n ends in 111. So the five steps between corners show the pattern of j mod 8, and from that the step to the touch id follows:

n ^ (n+1)Lwhen
190c1n even
3f140n = 1 mod 4
73242n = 3 mod 8
15f445n = 7 mod 16
313848n = 15 mod 32
63e051n = 31 mod 64
1271060n = 63 mod 128, and so on

The one blind spot: when j + 6 is a multiple of 8, the step to the touch id is L(15), L(31), L(63) or higher depending on bits of j that the corners never reveal. The server then lists all 13 candidates; half the time the right one is L(15). In practice a candidate list has matched only one tile every time.

K differs from tile to tile and no two of the 20 tiles are near each other in counter space, so the CRC input also holds per-tile data (a serial number, or counter bits above 16). It is not needed for prediction. How the model was found: L(4) turned out to be L(2) shifted one bit, which pointed at a shift register; the bit-reflected shift fit all measured values with one polynomial and then predicted the four carry values above with no free parameter.

Mapping touches to tiles

The server keeps data/touch-map.json: touch id to the six corner ids of its tile. It fills the map in three ways, in this order:

  1. Prediction. The first packet from an unknown touch id, hover included, is matched against every tile's predicted touch id(s). A unique match is stored at once. This is how new tiles get mapped in normal use.
  2. Automatic run. If prediction is ambiguous, a down or hold from an unknown id starts a mapping run: tiles without a touch id light up one at a time, top row first, and the next new id with a down or hold claims the lit tile. The id that started the run must lift first, since its finger is usually not on the lit tile. With a single unmapped tile it is assigned directly. Auto-start waits until the layout has been unchanged for 15 s, because a tile touched while the controller is still taking in new tiles is not in the list yet.
  3. Map touch button. The same run, started by hand. It visits only unmapped tiles; when every tile is mapped it remaps all of them. Any id can claim the lit tile, including one mapped earlier, so a wrong entry heals by touching the right tile.

Ids belong to the tile hardware: rotating a tile kept its mapping, and the layout change did not require a remap. Moving a tile to another position is expected to behave the same (untested).

What touches do once mapped is set in the Touch sheet of the main page: off, glow (touched and hovered tiles light up and fade), ripple (glow plus a ring spreading from the tile) or paint (fill the tile with the brush).
